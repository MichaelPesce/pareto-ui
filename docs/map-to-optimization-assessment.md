# Initial map-to-optimization assessment — 9 September 2026

**Historical research.** The basic workflow, explicit
planning horizon, input preservation, completion checklist, and solver-backed
feasibility check described below have since been implemented. Start with the
[workflow guide](scenario-completion.md) and [public practice files](../examples/map-to-optimization/README.md).
See [current validation behavior](scenario-validation.md) for implementation details
and limitations. The remaining sections record the original experiments and plan;
source links point to the revisions inspected at that time.

The map workflow can reach a real, feasible optimization with substantially less data than the toy workbook contains. I verified this with the installed parent model and CBC, including a temporary workbook generated from `map_testing/map_testing.kml`. The investigation recommended work to protect data during map/table synchronization, establish a reliable planning horizon, and replace the fixed table checklist with requirements derived from the selected facilities and optimization settings.

The experiments below preceded implementation of the completion workflow.

**Evidence and scope.** The inspected parent checkout was on `remove-tensorflow`, commit `df03357884ebd5a76ba47e6831a8deffdd2d9515`, with local changes in two utility files. The app's tested Python environment contained `project-pareto` version `1.2.dev0`, installed from that directory. The installed strategic model, data checks, common model builder, units conversion, and Excel reader matched the local files byte for byte when checked. These files, together with the UI's own reader and exporter, are the authority for the findings below. Newer upstream documentation can describe different behavior.

I read the toy workbook cells and a saved scenario created from it. Its saved status was Draft; its Excel snapshot and the supplied toy workbook produced identical model sets and parameters. The workbook has 52 periods, four production pads, one completions pad, two disposal sites, two external sources, three storage sites, two treatment sites, three reuse options, and nine network nodes. Those counts describe this example, not minimum requirements.

Experiments used temporary workbooks and model instances, without calling the live scenario handler or writing to the user's scenario database. Python: `pareto-ui-env-3.11`; solver: CBC; cost objective; distance-based pipeline CAPEX; input pipeline capacities; node capacities enabled; water quality, hydraulics, desalination surrogate, subsurface risk, and infrastructure timing disabled. Solver runs used scaling factor 1,000, zero optimality gap, a 45-second solver limit, and slack variables disabled. Apart from the shorter time limit, these are the saved toy scenario's effective settings. The experiments exercised model construction and solving, not the complete UI result-reporting path.

| Experiment | Observed result | Consequence |
| --- | --- | --- |
| Supplied toy workbook | CBC optimal; parent solution-feasibility check passed | A verified baseline for this installed version. |
| One production pad → one network node → one disposal site, two periods, 100 bbl/day | CBC optimal; feasibility check passed; objective 1.428 kUSD | Completions, external water, storage, treatment, reuse, and trucking are not universally necessary. |
| Same network with its first pipe limited to 50 bbl/day, no expansion | Model construction and parent aggregate checks passed; CBC infeasible | Total sink capacity is insufficient as a feasibility test. |
| Same network with its node-to-disposal connection removed | Model construction and aggregate checks passed; CBC infeasible | A disconnected disposal site must not count as accessible capacity. |
| Same network with no production forecast values | Model built; solver preparation failed with division by zero | Missing demand/supply data must not be treated as a completed scenario. The tested parent model also needs protection against zero-total-produced-water ratios. |
| Same network with empty expansion option sets | Construction failed with `max() arg is an empty sequence` | A mathematically simple network still needs compatible option-set structure in this implementation. |
| Same network with omitted operating costs | CBC optimal, but objective changed from 1.428 to 35.028 kUSD | “Solves” does not establish that costs are complete or realistic. |
| Same network with an empty `NodeCapacities` parameter | CBC optimal; node constraint skipped | Missing capacity can mean unrestricted capacity. |
| Same network with an explicitly empty `Economics` parameter | Construction failed with missing `discount_rate` | Missing, empty, and explicit zero are different states. |
| Map-generated three-node workbook, forecasts filled but no completions pads | Forecast indices rejected because `TimePeriods` was empty | There is a concrete horizon/export problem independent of physical feasibility. |
| Same workbook with `CompletionsDemand` time headers restored, still no completions pads | CBC optimal; feasibility check passed | The header dependency can be satisfied without inventing a completions facility or demand. |
| Actual KML geometry, only PP01 classified as production and K01 as disposal, other points retained as network nodes | CBC optimal; feasibility check passed for 52 weeks | A map-derived, positive-flow optimization is achievable with the present model. This was a deliberately simple demonstration, not an assertion about the intended roles of all map points. |

The two map formats produced the same 17 named points, 17 named paths, and 18 directed connections when imported with default node type `NetworkNode`. Coordinate differences were below 5 × 10⁻¹³ degrees. Under that import setting, names such as PP01 and K01 remain network nodes until classified; their names alone do not establish model roles.

The original experiments used local, untracked `map_testing/` files. For a reproducible starting point in a fresh clone, use the [public practice example](../examples/map-to-optimization/README.md).

**A concrete sufficient starting case.** The following is a small, verified recipe, rather than a claim that there is one universal minimum spreadsheet. Its purpose is to give the first guided workflow a precise acceptance target.

```text
P1 ──100 bbl/day──▶ N1 ──100 bbl/day──▶ K1
```

| Data | Values in the two-period experiment | Why it is present |
| --- | --- | --- |
| `ProductionPads`, `NetworkNodes`, `SWDSites` | P1, N1, K1 | Facility roles and identifiers. All other facility sets can be empty. |
| `TimePeriods` | T01, T02, in this order | A nonempty planning horizon shared by every forecast. For Excel input today, these come from `CompletionsDemand` headers, even with no CP rows. |
| `Units` | bbl, day, week decision period, mile, inch, USD, mg/liter, psi, foot, g | Supply and capacity are rates; inventory is volume. 100 bbl/day is 700 bbl in a weekly decision period. The model input key is `decision period`; UI display metadata uses `decision_period`. |
| `PNA`, `NKA` | `(P1,N1)=1`, `(N1,K1)=1` | Enabled, directed, supported connections. A line drawn on a map is not sufficient by itself. |
| `PadRates` | P1 = 100 bbl/day in both periods | Positive produced-water supply that must be managed. No completions or flowback values are necessary in this case. |
| `InitialPipelineCapacity` | 100 bbl/day on both pipes | Existing capacity sufficient for the required flow. |
| `InitialDisposalCapacity` | K1 = 100 bbl/day | A permanent destination with adequate capacity. `DisposalOperatingCapacity` was omitted and used the parent default 1; guidance should expose that assumption. |
| `NodeCapacities` | N1 = 100 bbl/day | Explicit throughput limit under the app's node-capacity setting. |
| `PipelineDiameters`, `PipelineDiameterValues`, `PipelineCapacityIncrements` | D0; diameter 0; increment 0 | The do-not-build option. This small experiment excludes new pipe capacity. |
| `InjectionCapacities`, `DisposalCapacityIncrements` | I0; `(K1,I0)=0` | A compatible zero-expansion option, including for the parent's aggregate checks. |
| `PipelineExpansionDistance` | 1 mile on each pipe | Required by the selected distance-based CAPEX configuration. |
| `PipelineCapexDistanceBased` | `pipeline_expansion_cost=100` USD/(inch·mile) | Required scalar input for this configuration. This is an arbitrary experimental value, not a proposed production default; no expansion is built. |
| `DisposalOperationalCost`, `PipelineOperationalCost` | 1 USD/bbl at K1; 0.01 USD/bbl per pipe | Explicit example economics. Total flow is 1,400 bbl; cost is 1,400 × (1 + .01 + .01) = 1,428 USD. |
| `Economics` | Parent fallback: discount rate .08, CAPEX lifetime 20 years | The experiment omitted this whole parameter. An explicitly empty parameter failed; the generated map template already supplies these values. |

The spreadsheet reader also supplies an internal `proprietary_data` flag. This is adapter metadata, not another user task. The parent fills other absent optional sets/parameters before constructing the model. Its table-name checks alone are not a complete input specification. See [required-data logic](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/process_data.py#L94), [parameter defaults](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/build_utils.py#L158), and [units handling](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/units_support.py#L49).

For the actual KML demonstration, the path PP01 → N01 → K01 carried 100 bbl/day for 52 weeks. K01 had capacity 100 bbl/day and cost 1 USD/bbl; network nodes had capacity 1,000 bbl/day. D4 was assigned to the map paths using the existing 4-inch/14,286 bbl/day lookup; active pipes used 0.01 USD/bbl. The template's existing expansion and economic defaults were retained. The planning headers and PP01 forecast were supplied in the temporary workbook. CBC returned a feasible optimum of 37.128 kUSD, consistent with 36,400 bbl × 1.02 USD/bbl.

At the time of this assessment, the app rejected this otherwise working small case because its checklist insists on completions pads, storage, external water, and their tables. That is an application restriction, not a demonstrated physical requirement. See [current minimum-table checklist](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/util.py#L686).

**How the requirements grow.** User guidance should follow the facilities and modes actually present. The entries below include inputs that need a deliberate value or a reviewed default for a useful result; they are not all hard errors in the parent library.

| When present or selected | Additional inputs and decisions |
| --- | --- |
| Completions pads | `CompletionsDemand` and `FlowbackRates` by pad and period; incoming routes for demand and outgoing routes for positive flowback; `CompletionsPadOutsideSystem`; `CompletionsPadStorage` and initial pad inventory if used; `PadOffloadingCapacity` for trucking; `ReuseOperationalCost`. Zero demand and zero flowback are valid during inactive periods, and an entire forecast may legitimately be zero. |
| External water sources | `ExtWaterSourcingAvailability` by source/period, `ExternalSourcingCost`, and permitted FCA/FCT delivery routes. They are unnecessary when other supplies meet demand. A source marker does not make fresh water available automatically. |
| Disposal sites | Existing capacity, operating fraction by period, operating cost, and any eligible new-build capacity/cost options. Explicit zero initial capacity and a missing capacity entry can behave differently: this parent implementation derives disposal expansion eligibility from the supplied initial-capacity entries. Existing positive-capacity sites are marked ineligible for expansion by that logic. |
| Storage | Initial capacity, `InitialStorageLevel`, allowed expansion sizes/costs, storage operating cost/revenue, and both filling/withdrawal routes as needed. Inventory must obey period balances. The current terminal inventory bound defaults to zero, so storage cannot be treated as unlimited permanent disposal. Parent storage loss and operating assumptions also need review. |
| Treatment | Technology and capacity options, `InitialTreatmentCapacity`, `TreatmentEfficiency`, treatment costs, technology/site desalination classification, and relevant removal/quality data. Outgoing routes need a stream meaning: 1 is treated water, 2 is residual water. The parent can skip a stream balance when that stream is not represented; the UI must make this boundary assumption explicit if it is allowed. |
| Beneficial reuse | `ReuseCapacity`, `ReuseMinimum`, `BeneficialReuseCost`, `BeneficialReuseCredit`, and an incoming route. A missing capacity uses the parent's unlimited-capacity sentinel; zero capacity prevents delivery. `ReuseMinimum` is a minimum **when the option is selected**, not an unconditional obligation to send water. An unusable optional reuse site is not automatically a globally infeasible scenario. |
| Trucking | Supported trucking arc entries, `TruckingTime` in hours, source-specific `TruckingHourlyCost`, and relevant offloading limits. Trucking is optional; FCT/CKT are not universal requirements. Pipe distance alone does not establish road travel time. |
| New infrastructure | Compatible option sets, zero/do-not-build options where appropriate, increments, and costs. Existing capacity may be zero if eligible new construction can meet the requirement. Keep the approved expansion defaults and expose which assumptions came from them. |
| Capacity-based pipeline CAPEX | `PipelineCapexCapacityBased` in place of distance-based costing inputs. |
| Calculated pipeline capacity | `Hydraulics` roughness/head-loss data and `PipelineDiameterValues`; do not imply that diameter alone establishes capacity in every mode. |
| Water quality enabled | `WaterQualityComponents`, source/pad/storage quality, treatment removal data, and applicable quality limits. Post-process quality and quality-constrained optimization have different meanings. |
| Hydraulics enabled | `Hydraulics`, `Elevation`, `WellPressure`, `InitialPipelineDiameters`, and diameter values; validate solver compatibility with the chosen formulation. |
| Infrastructure timing enabled | Relevant treatment, disposal, storage, and pipeline expansion lead-time tables. In the inspected implementation, the schedule calculation runs after solving; enabling it is not proof that construction availability was enforced throughout the optimization. |
| Environmental objective / subsurface risk / desalination surrogate | Emission coefficients; well proximity/pressure/risk inputs; or `DesalinationSurrogate` and compatible model/solver dependencies, respectively. These should not burden the basic cost workflow while disabled. |

The source defines these dependencies in [configuration and optional-data checks](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/process_data.py#L152). The [upstream strategic model documentation](https://pareto.readthedocs.io/en/latest/model_library/strategic_water_management/index.html) also explains zero-size construction options and treatment stream classifications; the installed source governs the exact implementation here.

**Why validation was misleading before the completion workflow.** It combines checks that are too strict in some places and too weak in others.

1. The fixed checklist requires all five major facility categories and a positive row total in each production, demand, and flowback forecast. It rejects valid simpler networks and valid all-zero inactive forecasts. Conversely, a positive row total does not prove every cell is numeric, finite, nonnegative, or belongs to the planning horizon. See [forecast helper](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/util.py#L145).
2. The parent required-data function mainly checks whether table/set **names** exist. Many optional-data checks warn and insert empty/default values. Empty named source/sink sets can satisfy its source/sink name check. It does not verify each facility's reachability, despite the introductory comment in the aggregate feasibility function suggesting that it does.
3. The application's third validation stage builds the model and runs aggregate supply/demand checks; it never invokes a solver. Construction already runs that parent check, so the app runs it again. Both the disconnected and bottleneck experiments passed construction, then proved infeasible with CBC. See [app feasibility check](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/util.py#L650) and [parent aggregate checks](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/process_data.py#L692).
4. A feasible solve can use surprising fallbacks. With wholly missing cost tables, defaults include disposal at 25 USD/bbl, sourcing at 150 USD/bbl, trucking at 15,000 USD/hour and 12 hours per trip, and piping at .01 USD/bbl. Partially specified cost tables can use 100 times the largest entered value for unspecified entries. Blank/nonpositive node capacities skip a capacity constraint. Distinguish unknown, explicit zero, explicit unrestricted, and accepted default; a universal “fill blanks with zero” action would be wrong.
5. The first checks use frontend JSON tables, while the model-building check reads the saved Excel file. The table-name check passes those frontend tables into a parent function that mutates its input dictionaries. Validation has no input/configuration revision attached to it. The Advance endpoint simply changes status. The run endpoint separately reconstructs settings and reads Excel. Synchronization and a final backend check need a shared contract. See [validation orchestration](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/scenario_handler.py#L924), [validation persistence](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/scenario_handler.py#L173), and [run configuration](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/routers/scenarios.py#L263).
6. Preliminary configuration construction omits desalination and subsurface-risk options that model construction accepts. More generally, validating before Optimization Setup cannot establish readiness for options the user changes later. See [configuration helper](https://github.com/project-pareto/pareto-ui/blob/e37dfe8fbe01c49d8f539be3383f86e50c74c1e4/backend/app/internal/util.py#L789).

The storage-expansion issue above was found by inspection, not independently demonstrated in a solver experiment: the aggregate routine filters `p_delta_Storage` keys by storage-site name, but that parameter is indexed by capacity option. It also passes a plain dictionary to a helper expecting a Pyomo parameter if that filter happens to match. See [storage aggregate calculation](https://github.com/MichaelPesce/project-pareto/blob/df03357884ebd5a76ba47e6831a8deffdd2d9515/pareto/utilities/process_data.py#L847).

**Original implementation sequence.** Keep the existing Map, Tables, Validate scenario, and Optimization Setup flow, while making the next needed action visible.

1. **Establish one input snapshot and preserve user data.** Define a normalized scenario input with stable facility/arc identifiers, an ordered horizon, units, table data, and optimization settings. Treat map and Excel as representations of that data. Preserve every table field the map cannot express. Add an input/configuration revision and make export, validation, and solving consume the same snapshot. Complete the four first-priority preservation fixes above before calling the workflow stable. Keep the user's existing expansion defaults.
2. **Implement a versioned requirements catalog for the current model.** Rules should declare when an input applies, its indices and units, legal domains, default behavior, severity, and explanation. Share the settings conversion used by validation and solving. Start with the verified basic cost case, then add each optional facility/mode. The parent library remains a construction check, not the UI specification. Keep advanced choices available, but flag unsupported combinations explicitly.
3. **Add a scenario-completion panel to Data Input.** Present “Network,” “Planning periods and forecasts,” “Capacity,” and “Costs and assumptions,” with counts of outstanding items. Clicking an item selects the affected map feature or opens the exact table row/period. Classify map points first; review directions; set the horizon; enter production/demand/flowback; provide route and destination capacity; review costs/defaults. Show only applicable sections, with the full table browser still available. Allow deliberate fill-zero for inactive forecasts and fill-constant/paste for selected periods; show the scope of changes before applying bulk edits. Do not infer production, demand, costs, or disposal availability from coordinates.
4. **Replace the validation result with actionable, deterministic issues.** Each issue should carry a stable code, severity, affected feature/table/row/period, actual and expected values with units, reason, and suggested action. For example: “P1 produces 100 bbl/day in T02, but its only outgoing pipe carries at most 50 bbl/day; review capacity, an eligible expansion, or another route.” Check identifiers, numeric domains, complete applicable forecasts, unit conversions, horizon alignment, directed reachability, accessible capacity, period balances, storage inventory, and selected build eligibility. Distinguish warnings about unused optional facilities from blockers on required flows. Guidance must work with AI entirely unavailable.
5. **Separate input readiness from solver evidence.** Fast checks should return “Inputs complete” or specific blockers. Then build the actual selected model from that revision. A bounded feasibility solve with slacks disabled can provide “Feasible plan found,” “Infeasible,” or “Not determined within the time limit.” An LP relaxation can supply an earlier infeasibility screen; LP feasibility alone is insufficient for the integer model. A feasible incumbent is sufficient for readiness even if optimality is not proved; no incumbent at timeout is not proof of infeasibility. If using a separate slack-based diagnostic solve, label it as diagnostic and quantify unmet requirements. Constraint scans of failed/uninitialized model values are not proof of the root cause. Recheck after Optimization Setup changes and enforce this at the run endpoint, not only through the Advance button.
6. **Prove the complete workflow with acceptance cases.** Turn the minimal positive-flow case into a maintained regression fixture; add equivalent KML/ZIP paths through import, classification, horizon, forecasts, validation, save/reload/export, optimization, and result display. Retain the toy workbook as the complex working baseline. Cover bottlenecks, reversed/disconnected routes, zero-activity periods, empty horizons, missing versus explicit-zero capacities, optional reuse absent/present, treatment streams, trucking persistence, forecast reordering, unit conversions, and changed settings after validation. Report-generation failure must remain distinct from solver failure.

The first delivery should be a dependable **map → simple cost optimization → results** path, with no mandatory completions, storage, external water, treatment, reuse, or trucking. Subsequent deliveries can extend the same requirement and guidance framework to those features. This avoids making the toy workbook's full table inventory a prerequisite for every user and gives each added feature a reproducible working example.
